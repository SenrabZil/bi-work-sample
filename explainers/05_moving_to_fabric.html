01

Built to move

The model already matches how Microsoft Fabric works. The layers (source, silver, gold) map onto a lakehouse. The files are plain text in Git, which Fabric workspaces can sync with. Row-level security lives in the model, so it travels with it. And there are no DAX calculated columns, which Direct Lake tables don't support.

02

Import or Direct Lake, table by table

An Import table holds its own copy of the data, rebuilt at every refresh. A Direct Lake table reads Delta tables from OneLake straight into memory.

For a model this size, Import is still a perfectly good answer: the lookup tables and annual figures load in seconds. Monthly trade is the table that grows, so it's the natural first move to Direct Lake. Mixing the two in one model needs Direct Lake on OneLake, which supports composite models.

03

Report or data app?

Fabric data apps are web apps hosted in Fabric that query a published semantic model in DAX, the same way a report does. Users sign in with their work account and row-level security still applies. Everything is written in code, usually with a coding agent, and the feature is in preview.

04

The model becomes the contract

The report and any app read the same measures, so a number can't differ between them. That also changes a design choice from lesson 02: the 97 per-tile text measures exist because report visuals can only bind to one measure. An app can read the register directly, so there they could collapse to a single lookup.

Data apps were in preview as of September 2026, and Fabric features move quickly. Check the current Microsoft documentation before relying on any detail here.

05

The rule, in one breath

Move the floor, not the house: rebuild the layers underneath and keep the model on top.

Choose Import or Direct Lake per table, not per model. Keep standard pages in Power BI, and add data apps only where they do something a report can't.
