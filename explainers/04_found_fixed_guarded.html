Version control, a validator and a review that questioned the validator. How a quiet gap was found, fixed and guarded against.

with Elizabeth Cecilia. Green lights are only as honest as the tests behind them.

01

Everything is a text file

The report and model are saved as a Power BI Project: the model in TMDL, the pages and visuals in JSON, all in Git. Every change can be read line by line, compared and rolled back. A validator script checks the files against the model and page specifications after every build.

A validator is only as good as its checks. This lesson is about a check that passed when it shouldn't have.

03

Why it slipped through, and the fix

The old check confirmed that each subtitle named a basis measure. It never confirmed that the measure existed. The two short versions were never generated, because those tiles had been planned as tables and became cards later.

The fix had two parts. Add the two missing measures, and add a check that every field the report names exists in the model: visual fields, filters, sorts, subtitles, tooltips and colour rules. That added 263 checks. It was tested both ways: it failed on exactly the five broken cards before the fix, and passes after it.

The unused items are mostly deliberate: a full basis line behind a card that shows the short one, or register rows for tiles not yet built. Deleting them would break the specification, so they get hidden.

Card titles and values above are placeholders; the checks and counts are real. The review itself was done by a coding agent and checked by a person, which lesson 07 covers.

05

The rule, in one breath

A passing check proves only what it tests. When something slips through, fix it and add the check that would have caught it.

Plain-text files in Git, a validator after every build, and a review that questions the validator itself. Found, fixed, guarded.
